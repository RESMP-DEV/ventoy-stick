# Ventoy provisioning stick (Ubuntu 26.04.1 + Codex + CCR + GLM-5.3)

Built 2026-09-23 from the M4 Max (main machine). Profile-based since 2026-09-23:
each person/machine is a bundle under `provision/profiles/<name>/`.

| Path | What |
| --- | --- |
| `ubuntu-26.04.1-live-server-amd64.iso` | Server install, wired to Ventoy auto_install |
| `ubuntu-26.04.1-desktop-amd64.iso` | Desktop install (manual, then bootstrap) |
| `ubuntu-24.04.4-desktop-amd64.iso` | Legacy ISO (restored from previous stick contents) |
| `ventoy/ventoy.json` | Menu aliases + auto_install binding (template list per profile) |
| `ventoy/autoinstall/<profile>.user-data` | Cloud-init autoinstall seed per profile (GENERATED by `tools/make-profile.sh`; edit the generator, not this file) |
| `provision/profiles/<name>/profile.conf` | Identity + capability flags for that profile |
| `provision/profiles/<name>/ssh/*.pub` | authorized_keys for that profile's user |
| `provision/profiles/<name>/secrets.tar` | codex auth + ccr config + runtime creds (+ zcode creds) |
| `provision/bin/` | Static Linux x86_64: codex (rust-v0.154.0), codex-code-mode-host, ccr-rust |
| `provision/files/` | Shared router configs (env placeholders), model catalog, baseline installer, policy file (`AGENTS-core.md`, internal-only) |
| `provision/bootstrap.sh`, `provision/ccr-serve.py` | Provisioner + service launcher |
| `provision/latehook.sh` | Installer-env late-command hook: SSH key fallback, first-boot retry unit, non-fatal bootstrap run, logs to the stick |

## Profiles

One profile = one person/machine: username, realname/email, hostname, SSH keys,
capability flags (`ENABLE_CCR_MAIN` 3456 listener, `ENABLE_GLM_WORKERS` 3457
GLM path, `ENABLE_ZCODE_CREDS`), and its own `secrets.tar` (own codex auth, or
the Mac's shared creds when created `--from-mac`).

Stand-up layer flags (executed by `bootstrap.sh` in full mode; see
`BRINGUP.md` for the manual steps they replace):

- `ENABLE_PASSWORDLESS_SUDO` — `/etc/sudoers.d/<user>` NOPASSWD fragment,
  visudo-validated; also written by the seed's late-commands so it exists
  before first boot.
- `ENABLE_BUILD_CACHE` — sccache via absolute-path cargo wrapper +
  `/etc/profile.d/00-build-cache.sh` + ccache 50G/inode_cache config +
  `/usr/local/bin/sccache` symlink.
- `ENABLE_POLICY_FILES` — installs `files/AGENTS-core.md` as `~/AGENTS.md`,
  `~/.codex/AGENTS.md`, plus the `~/.claude/CLAUDE.md` `@~/AGENTS.md` stub.
- `ENABLE_CLAUDE` (+ `CLAUDE_MODEL_TIER`) — native Claude Code install,
  `claude-ccr` launcher, `~/.claude/settings.json` routing, and a
  marker-checked smoke through ccr-main.
- `ENABLE_NVIDIA` (+ `NVIDIA_DRIVER_PKG`) — driver from the Ubuntu repo
  (open kernel modules; Secure Boot must be off), persistence daemon
  enabled, nvtop. `ENABLE_CUDA` adds `nvidia-cuda-toolkit`.
- `ENABLE_ZEROTIER` (+ `ZT_NETWORK_ID`) — install + `join`; Central
  authorization stays manual by design.

- Boot menu: with more than one profile, Ventoy shows a template menu when you
  boot the server ISO; each entry installs Ubuntu as that profile unattended.
- Desktop flow: `sudo bash /media/$USER/Ventoy/provision/bootstrap.sh --profile <name>`
  (omitting `--profile` uses `default`).
- Add a person from the Mac:
  ```
  tools/make-profile.sh --name alice --user alice \
      --realname 'Alice Doe' --email alice@example.io --hostname compute2 \
      --ssh-pub ~/path/to/alice.pub --from-mac            # shared GLM creds
  tools/sync-stick.sh

A GPU machine with the full stand-up layer (sudo, caches, policy, Claude,
NVIDIA + CUDA, ZeroTier) is one more line of flags:

  tools/make-profile.sh --name bob --user bob \
      --realname 'Bob Roe' --email bob@example.io --hostname gpu1 \
      --ssh-pub bob.pub --from-mac --nvidia --cuda --zerotier <network-id>
  tools/sync-stick.sh
  ```
  Their own credentials instead of the Mac's: pass `--secrets-dir DIR` with
  `codex/auth.json`, `codex/config.toml` (use `__HOME__` for the home path),
  `ccr/runtime-credentials.json`, optional `zcode/`. Codex-only, no GLM:
  `--no-glm --no-main --no-zcode`.

## Flow A: server ISO, unattended (recommended for the compute machine)

Redesigned 2026-09-26 after the root cause was found: **on a Ventoy boot the
read-only ISO device-mapper marks the WHOLE stick disk read-only for the
entire live session, and no mount of the data partition — rw or ro, via node
or dm copy — can succeed.** That single mechanism aborted every install at
the stick-mount late-command (after a complete install) and explains why no
logs ever reached the stick. The install therefore touches the stick NOT AT
ALL: the seed (which Ventoy injects reliably via CIDATA) carries the SSH keys
and writes the first-boot completion unit directly into the target.

1. Boot the stick and explicitly choose **Ubuntu 26.04.1 Server ... AUTOINSTALL**.
   This profile wipes the largest eligible disk and uses a GPT/EFI layout;
   boot the installer in UEFI mode. The unattended install ends **powered off**.
   It cannot fail on the stick anymore: late-commands only write to /target.
2. **Leave the stick inserted (or re-insert it) and power the machine on.**
   First boot mounts it as a normal writable USB disk (no Ventoy hold when
   booting from the internal disk) and `provision-retry.service` completes all
   provisioning from it: binaries, credentials, baseline tools, the stand-up
   layer (sudo, build caches, policy files, Claude Code + claude-ccr, NVIDIA
   driver + persistence + optional CUDA, ZeroTier join), the CCR listeners,
   and marker-checked Codex and Claude smokes. Baseline has a 30-minute
   limit; the service a 75-minute limit. `/root/BOOTSTRAP-OK` appears only
   after every required step passes; failures create `/root/BOOTSTRAP-FAILED`
   + nonzero `/root/BOOTSTRAP-RC` and retry on the next boot (with the stick
   inserted). The verdict line ends with per-stage statuses:
   `RESULT: mode=full baseline=ok ... smoke=ok sudo=ok caches=ok policy=ok
   claude=ok claude_smoke=ok nvidia=ok cuda=ok zt=ok`.
   ```sh
   sudo systemctl status provision-retry.service
   sudo tail -100 /var/log/ventoy-bootstrap.log
   sudo systemctl restart provision-retry.service   # after fixing something
   ```
3. The box records its own network identity every boot until completion:
   `logs/firstboot.log` on the stick gets one line per boot with its IP
   addresses, and `/root/FIRSTBOOT-NETWORK` on the machine holds the
   timestamped `ip addr` + routes (read it from console if SSH discovery
   fails). After provisioning completes, `logs/firstboot-<ts>/` on the stick
   receives `FIRSTBOOT-NETWORK` and the full bootstrap log. Pull the stick
   once done; the Ventoy default entry is the manual Desktop ISO, so leaving
   it in cannot silently re-wipe.
4. If the installer itself still errors, its diagnostics land on the installed
   disk at `/root/install-failure/` (journal, `/var/log/installer` tar, blkid,
   lsblk); a fatal install error also runs error-commands, which never touch
   the stick (impossible during a Ventoy session).
5. Initial console password: the profile's `INITIAL_PASSWORD` (plain text only
   in the profile on the stick; crypted into the seed). SSH is key-only, using
   the keys embedded in the seed (installed by subiquity itself, independent of
   any later step). After provisioning, `~/.local/bin/ccr-healthcheck` tests
   the local GLM listener.
6. Change the console password with
   `sudo bash /mnt/ventoy/provision/bootstrap.sh --reset-password` (stick
   inserted), or adjust and re-run `provision-retry.service`.

Refresh installer commands without changing a profile's existing identity,
password, keys, or credentials:
```sh
tools/make-profile.sh --name default --refresh-only
tools/sync-stick.sh
```

## Flow B: desktop ISO, manual

1. Boot the stick, choose **Ubuntu 26.04.1 Desktop**, install normally.
2. Plug the stick back in if needed, then one command:
   ```
   sudo bash /media/$USER/Ventoy/provision/bootstrap.sh
   ```
   Installs everything including credentials, starts services, runs
   healthcheck + codex smoke test.

## What "Codex + GLM-5.3" means on the box

Identical topology to the Mac (see `~/.claude-code-router/LOCAL_SETUP.md`):

- `codex` (static musl binary, openai/codex rust-v0.154.0, same release as the Mac)
- `ccr-rust` (static musl build of the same source; staging edit: vendored OpenSSL)
- systemd **user** services `ccr-main` (127.0.0.1:3456, zai/azure/minimax) and
  `ccr-glm-workers` (127.0.0.1:3457, GLM-only native Responses, effort=max passthrough)
- Default `~/.codex/config.toml` = the CCR GLM profile, so plain `codex` runs
  `zai,glm-5.3-flashx` via 127.0.0.1:3457; `codex-ccr` and
  `ccr-glm-workers-local {start|stop|restart|status}` mirror the Mac launchers.
- ZCode credentials are installed under `~/.zcode/v2/` for any future ZCode CLI
  (no official Linux ZCode distribution exists as of 2026-09-23; npm `zcode` is a squatter).

## Secrets handling

- Owner decision (2026-09-23): this is an internal two-machine tool, so the
  bundle ships **unencrypted** as `provision/profiles/<name>/secrets.tar`
  (installed with mode 0600). Nothing is typed or re-authenticated on the box.
- Re-bundle a profile after rotating any key on the Mac:
  re-run `tools/make-profile.sh` with the same `--name` (+flags), then `tools/sync-stick.sh`.
- If the stick is lost: it contains ZAI/Azure/Minimax API keys, the codex
  bearer, and ZCode OAuth material. Revoke/rotate those.

## If the installer errors out before installing

When subiquity rejects or crashes on the seed, it shows an error and leaves a
shell; nothing reaches the stick (early-commands never ran = no
`logs/started-*/`). Capture everything in one paste at that shell (root, live
environment):

```sh
mkdir -p /mnt/v; mount /dev/disk/by-label/Ventoy /mnt/v 2>/dev/null; d=/mnt/v/logs/error-shell-$(date +%Y%m%d-%H%M%S); if ! [ -d /mnt/v/provision ]; then mkdir -p /target/root/error-shell; d=/target/root/error-shell; fi; mkdir -p $d; { cp -a /var/log/installer /var/crash $d/ 2>/dev/null; journalctl -b > $d/journal.txt 2>&1; cat /dev/vcs1 > $d/tty1-screen.txt 2>/dev/null; dmesg > $d/dmesg.txt; lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINT > $d/lsblk.txt; blkid > $d/blkid.txt; cat /proc/cmdline > $d/cmdline.txt; ip -4 addr > $d/ip-addr.txt; }; sync; [ -d /mnt/v/provision ] && umount /mnt/v; echo DONE-$d
```

If the stick refuses to mount, the dump lands in `/target/root/error-shell`
(on the machine's disk) instead, and this single extra command tells us WHY
the mount failed (its `rc` and the kernel message are the diagnosis):

```sh
mount /dev/disk/by-label/Ventoy /mnt/v; echo rc=$?; dmesg | tail -20
```

`tty1-screen.txt` captures the exact error text the screen showed; the
subiquity traceback is in `/var/log/installer/subiquity-server-debug.log`.
The stick-side helper `provision/dump-error-shell.sh` does the same and more
(runs `bash <stick>/provision/dump-error-shell.sh` after mounting).

The 2026-09-26 diagnosis: the seed (current AND the attempt-2 variant) passes
the complete merged schema of subiquity 7403 extracted from this exact ISO
(base schema + every controller's `autoinstall_schema`; `shutdown: poweroff`,
`error-commands`, `early-commands`, `ssh.authorized-keys` all valid), so a
schema rejection is ruled out; remaining suspects are runtime-level storage
validation on the target machine, Ventoy-side injection, or an error outside
the seed entirely — the error-shell dump settles it.

## Known caveats

- The autoinstall storage matcher uses `size: "largest"` among eligible disks.
  Equal-sized disks are not an interactive safety prompt; check the target
  layout before choosing the unattended Server entry.
- Desktop autoinstall is intentionally NOT wired (unverified on the flutter
  installer); desktop uses Flow B.
- exFAT: the stick's data partition was reformatted NTFS -> exFAT so the Mac can
  write it; Ventoy scans any supported FS. Binaries lose the exec bit on exFAT,
  which `bootstrap.sh` restores via `install -m 755`. The label must be exactly
  `Ventoy` (the late-commands mount `by-label`): verify with
  `diskutil info Ventoy` on the Mac before an unattended run.
- Ventoy version must be >= 1.1.12 (v1.1.11 crashed subiquity disk probing on
  Ubuntu 24.04+; check the version banner at the Ventoy boot menu).
- The install now ends POWERED OFF (`shutdown: poweroff`) so a forgotten stick
  can never re-trigger the autoinstall wipe; `VTOY_DEFAULT_IMAGE` is the manual
  desktop ISO as a second guard.
- `/root/provision-copy` (incl. `secrets.tar`, mode 600 under `/root`, mode 700)
  is intentionally kept on the installed system: it is the first-boot retry and
  `--finish-secrets` source. Wipe it manually if that is unacceptable.
- `bootstrap.sh --chrooted` stages files only. First boot completes setup via
  `provision-retry.service`, with an explicit user-manager bus environment.
- The stand-up layer runs in full mode only (it needs network + a real
  system); the autoinstall seed independently writes the sudoers fragment so
  sudo works from the very first boot even if provisioning stalls.
- Internal-only files (`files/AGENTS-core.md`, the real
  `files/ccr/*.json`, all real profiles, and the generated
  `ventoy/autoinstall/*.user-data` + `ventoy.json`) are excluded from the
  public git repo by `.gitignore`; the staging tree keeps them so
  `tools/sync-stick.sh` still deploys the full stick. Refresh
  `files/AGENTS-core.md` from the control machine's `~/AGENTS.md` (strip the
  `@LEAN-CTX.md` import line) whenever the core policy changes.
- The baseline ships the standalone `hfd-cli` wheel and installs the Rust build
  prerequisites needed by `cargo-audit` and `cargo-deny`. First boot needs network
  access for the remaining packages and the model smoke request.
- Rebuilding from `dist/ventoy-provision-kit/` alone is NOT possible: the kit
  snapshot lacks `provision/bin/`, `profiles/`, and `ventoy/autoinstall/`.
